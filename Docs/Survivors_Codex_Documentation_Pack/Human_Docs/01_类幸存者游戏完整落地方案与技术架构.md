# 类幸存者游戏完整落地方案

## 1. 项目目标

建立一个独立、可商业化、可扩展的类幸存者游戏框架。框架完成后，团队应能持续新增角色、技能、被动、构筑联动、敌人、Boss、地图、波次、难度和局外成长，而无需反复修改核心系统。

项目不是开源游戏换皮，也不复用参考项目中的美术、特效、角色、地图、Prefab、Scene、动画、音频、字体、Shader 或品牌元素。所有正式表现资源后续通过自有生产流程创建，其中 AI 生成资源必须留存完整来源记录并经过人工审核。

## 2. 技术基线

| **领域** | **决策**                                                    |
|----------|-------------------------------------------------------------|
| 引擎     | Unity 6 LTS，锁定 ProjectVersion.txt 中的准确补丁版         |
| 渲染     | URP；初始支持 2D/2.5D 顶视角                                |
| 语言     | C#                                                          |
| 首发平台 | Windows x64 + Steam                                         |
| 输入     | Unity Input System；键鼠与主流手柄                          |
| 资源     | Addressables；本地 Catalog 起步，后续可扩展远程 Catalog/DLC |
| 本地化   | Unity Localization；简体中文、英文、伪本地化                |
| 测试     | Unity Test Framework；EditMode、PlayMode、Soak Test         |
| 性能     | 先正确的单线程数据导向实现，再按测量结果迁移 Jobs/Burst     |
| 平台     | IPlatformFacade 隔离；先用 Null 实现，后接 Steam            |
| 内容     | ScriptableObject 作者数据 → 验证/烘焙 → 纯运行时定义        |

## 3. 成功标准

框架完成后必须证明：

1\. 新角色可通过配置和资源新增，不修改核心程序集。

2\. 使用现有效果模块的新技能可完全通过配置新增。

3\. 新构筑由标签、条件、联动和进化配方形成，不创建硬编码“流派类”。

4\. 新地图由地图定义、场景、地图运行时和遭遇表组合完成。

5\. 表现资源可整体替换而不影响模拟规则。

6\. Steam 不可用时，本地版本仍可完整运行。

7\. 内容、存档和构建均有版本与校验机制。

8\. 正式构建无法混入 Placeholder 或无来源记录的正式资源。

9\. 固定随机种子的核心测试可复现。

10\. 压力运行没有持续内存增长或高频 GC。

## 4. 扩展等级

### 4.1 数据扩展

不修改核心代码即可新增：

- 角色、初始技能、角色 Trait

- 技能、被动、状态效果组合

- 敌人、Boss、掉落表

- 构筑联动、武器进化

- 地图、遭遇表、刷怪阶段

- 局外升级、解锁条件、难度

- 视觉与音频 Profile

### 4.2 逻辑模块扩展

遇到已有模块无法表达的新机制时，新增一个实现统一接口的模块并注册。例如时间倒流、伤害传播、分身重放、地图腐化。新增模块不得要求修改已有角色、技能或地图配置。

### 4.3 引擎后端替换

通过接口替换：

- 管理数组 → Jobs/Burst 后端

- SpriteRenderer → GPU Instancing

- 本地保存 → Steam Cloud 同步

- 有限竞技场 → 无限区块地图

- Unity 粒子 → 自定义 GPU 特效

上层内容格式保持不变。

## 5. 明确不做

框架阶段不做：

- 多人联机

- 运行时用户脚本 Mod

- 外部 C# DLL 热加载

- 正式剧情系统

- 大量正式角色或武器

- 在线账户、付费、排行榜

- 复杂 Steam SDK 集成

- 运行时生成 AI 美术

- 试图取代 Unity Entities 的通用 ECS

## 6. 工程原则

- 模拟层只认识数字、稳定 ID、运行时索引、标签和实体句柄。

- 模拟层不知道 GameObject、Transform、Prefab、Sprite、AudioClip、Scene 或 Steam。

- 表现层只消费快照与事件，不拥有战斗真值。

- 高频实体不使用逐实体 MonoBehaviour 更新。

- 不使用 GameObject.Find、FindObjectOfType、全局 Service Locator 或随意的静态 Singleton。

- 不在高频路径使用 LINQ、反射、字符串格式化或临时集合。

- 运行开始后，高频对象通过池和数据 Store 管理。

- 所有架构重大决策写入 ADR。

- 所有里程碑必须有可执行测试和可审计结果。

## 8. 商业化边界

- 根目录许可证不代表仓库中所有资产都拥有相同授权。

- 所有外部代码、字体、音频、插件和素材必须单独记录。

- 无许可证的公开仓库不能作为复制来源。

- 正式 AI 资源必须保存工具、模型版本、日期、提示词、输入引用、人工修改和文件 Hash。

- 上线前按当时最新的 Steam、引擎、插件与司法辖区要求复核；本文档是工程流程，不是法律意见。

# 产品范围与边界

## 产品定位

单人、俯视角、自动或半自动攻击、局内成长、局外解锁的类幸存者游戏。首发目标为 Windows/Steam。框架支持后续扩展，但首个垂直切片只验证核心循环和差异化机制。

## 框架完成前的测试内容

只允许程序化占位内容：

- 2 个测试角色

- 4-6 个测试技能

- 3 个测试被动

- 4 个测试敌人

- 1 个测试 Boss

- 2 张测试地图，其中一张用于证明新增地图流程

- 2 个构筑联动

- 1 个进化配方

测试内容不代表最终世界观和美术方向。

## 垂直切片建议范围

框架冻结后，首个商业验证切片建议包含：

- 1 个正式角色

- 8 个正式技能或武器

- 8-10 种普通敌人

- 1 个 Boss

- 1 张正式地图

- 15 分钟完整局

- 20-30 个局内升级选项

- 1 条局外成长线

- 简体中文和英文

- 键鼠及手柄完整流程

## 非目标

- 复杂联机同步

- 大型开放世界

- 用户生成内容平台

- 依赖在线服务器才能运行

- 游戏内运行时生成视觉资源

- 首版即支持所有桌面和主机平台

## 设计守则

- 机制差异化优先于内容堆量。

- 每个新增系统必须说明它如何被多个角色或技能复用。

- 任何一次性专用逻辑，优先重构为 Trait、Effect、Condition 或 Map Module。

- 仍无法复用时，允许专用模块，但必须通过注册表接入，不能改写核心管线。

## 5. 实体模型

不编写通用 ECS，只实现游戏所需的紧凑 Store：

- ActorStore

- ProjectileStore

- AreaStore

- PickupStore

- SummonStore

Store 使用 Dense Array、Swap-back Remove、Free List 和 Generation。实体句柄：

> public readonly struct EntityHandle  
> {  
> public readonly int Index;  
> public readonly ushort Generation;  
> }

删除实体后递增 Generation，旧句柄不能引用新实体。

## 6. 空间查询

统一空间网格服务用于最近目标、投射物碰撞、范围伤害、拾取吸附、敌人分离和裁剪。

> cellX = floor(position.x / cellSize)  
> cellY = floor(position.y / cellSize)  
> cellKey = Hash(cellX, cellY)

禁止每个技能遍历全部敌人。

## 7. 表现层

表现层只接收：

- Render Snapshot

- Simulation Event

- View Spawn/Release Request

- VFX/Audio Request

ActorView、ProjectileView 和 PickupView 只更新显示和提交输入，不计算伤害、经验、死亡或掉落。

# 内容系统与数据结构规范

## 1. 稳定 ID

所有内容使用命名空间字符串 ID，不使用 enum 表示具体内容。

> base.character.test_runner  
> base.skill.arc_bolt  
> base.status.burning  
> base.enemy.slime_basic  
> base.map.test_arena  
> base.synergy.fire_overload

规则：

- 小写字母、数字、下划线和点号。

- 点号用于层级。

- 发布后不得修改。

- 显示名称与 ID 分离。

- 存档保存稳定 ID，不保存运行时索引。

- 运行时映射为紧凑 RuntimeContentIndex。

- 不只保存 Hash，始终保留原始字符串。

## 2. 内容包

> {  
> "packId": "com.studio.base",  
> "version": "0.1.0",  
> "schemaVersion": 1,  
> "minimumGameVersion": "0.1.0",  
> "dependencies": \[\],  
> "catalogAddress": "packs/base/catalog",  
> "assetLabel": "pack.base",  
> "official": true  
> }

> 读取 Manifest

> -\> 检查重复 ID

> -\> 加载必要资源  
> -\> 进入游戏

第一阶段不允许内容包覆盖相同 ID。补丁覆盖机制以后通过显式 PatchTarget 设计。

Delivery：Instant、Projectile、Area、Aura、Orbit、Beam、Chain、Summon、Trap。

# 技能与效果模块规范

## 1. 设计目的

绝大多数新技能应通过已有模块组合完成。只有无法表达的新机制才增加 C# 模块。

## 2. 烘焙操作码

> public struct EffectOp  
> {  
> public EffectOpCode Code;  
> public float Value0;  
> public float Value1;  
> public float Value2;  
> public int Int0;  
> public int Int1;  
> public RuntimeContentIndex Reference0;  
> public RuntimeContentIndex Reference1;  
> public EffectOpFlags Flags;  
> }

作者数据在构建或内容烘焙时转换为 EffectOp\[\]。高频执行路径不反射 ScriptableObject 类型。

## 5. 调用链保护

每个伤害包和技能触发上下文必须携带 ProcDepth、来源 ContentId 和调用链标记。达到上限后中止二次触发并写入诊断计数，避免无限递归。

## 6. 新模块准入

新增模块前必须回答：

1\. 现有模块组合为何不能表达？

2\. 新模块能否被至少两个未来内容复用？

3\. 是否改变模拟管线顺序？

4\. 是否影响存档格式或内容 Schema？

5\. 是否需要 Burst/Jobs 兼容？

6\. 是否有单元测试和性能测试？

新增模块需附 ADR 或 Change Request。

## 1. 文件拆分

> settings.json

## 3. 强制要求

- Schema 版本化

- 原子写入

- 临时文件

- 前一版本备份

- 校验和

- 显式迁移链

- 缺失内容容错

- 保存稳定 ContentId

- 不保存运行时索引

- 不保存 Unity Object 引用

- 本地保存不依赖 Steam

## 4. 接口

> public interface ISaveStorage  
> {  
> ValueTask\<SaveReadResult\> ReadAsync(  
> string slot,

>   
> ValueTask\<SaveWriteResult\> WriteAtomicAsync(  
> string slot,

## 5. 迁移

每次 Schema 变化添加一个单向迁移：

> v1 -\> v2  
> v2 -\> v3

禁止在加载器中堆积无法测试的条件分支。所有历史迁移必须有固定样本测试。

## 6. 内容缺失

当存档引用已删除内容：

- 保留原始 ID 供诊断。

- 使用明确的 Missing Content 结果，不抛出未处理异常。

- 对解锁项可忽略但记录警告。

- 对装备或局内恢复，按文档化规则替换、移除或终止恢复。

- 不静默映射到错误内容。

## 7. 云同步边界

Steam Cloud 是同步层，不是核心保存实现。平台层负责上传、下载、冲突检测和用户选择；ISaveStorage 仍然以本地原子文件为真值来源。
