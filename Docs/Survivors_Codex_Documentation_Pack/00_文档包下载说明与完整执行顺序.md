# Survivors Codex 文档包下载说明与完整执行顺序

版本：1.1  
日期：2026-07-24

本说明对应《类幸存者游戏 Codex 交付文档包》。文档包用于从零搭建一个可商业化、可持续扩展的 Unity 类幸存者游戏框架，并将后续角色、技能、构筑、敌人、地图及正式 AI 美术生产纳入可验证的工程流程。

核心约束：

- 新建干净工程，不 fork 任何参考游戏工程。
- 不复用参考开源项目的角色、美术、场景、特效、音频、Prefab、动画、材质、Shader、字体或品牌资源。
- 框架阶段只使用程序化占位资源。
- 正式内容后续重新设计和生产，并为 AI 生成资产保留来源、模型、提示词、输入参考、人工修改和文件 Hash 记录。
- Codex 每次只执行一个里程碑；测试、验证和构建未通过时，不得进入下一阶段。

# 四、完整执行顺序

## 阶段 0：人工初始化

在调用 Codex 前，由人工完成：

1. 安装并选定一个 Unity 6 LTS 补丁版本。
2. 创建全新的 URP 项目，不 fork 参考游戏工程。
3. 等待 Unity 完成 Package、Shader 和 Library 导入。
4. 初始化 Git，确认工作区干净。
5. 建立初始空工程提交和基线标签。
6. 将 `Repository_Docs/` 中的内容复制到 Unity 仓库根目录。
7. 将 `Templates/` 复制到仓库合适位置。
8. 填写 `Templates/PROJECT_VARIABLES.md`。
9. 把实际 Unity 版本写入 `Docs/ADR/0001-unity-version.md`。
10. 检查仓库，确认不存在参考项目的角色、美术、场景、特效、音频、Prefab 和动画资源。

人工初始化完成后，生成一次干净工程基线：

```text
git status
Unity 项目编译
空 EditMode 测试
空 PlayMode 测试
Windows Development Build
```

只有基线成立，才进入 Codex 自动实施。


- 绕过失败测试或验证器
- 把没有执行的检查报告为通过
- 在缺少批准的情况下改变程序集依赖、Schema、存档格式或 Tick 频率

## 阶段 4：里程碑审查门禁

每个里程碑实现结束后，使用：

```text
Prompts/13_MILESTONE_REVIEW_GATE.md
```

每项审查结果只能是：

```text
PASS
FAIL
NOT RUN
```

定义：

- `PASS`：检查实际执行，证据完整，结果满足要求。
- `FAIL`：检查执行，但结果不满足要求。
- `NOT RUN`：检查未执行、环境缺失或没有可靠证据。

禁止行为：

- 将手工观察描述为自动测试通过。
- 将 `NOT RUN` 当作 `PASS`。
- 在存在编译错误、失败测试或失败验证时宣称里程碑完成。
- 只给结论，不给命令、日志或产物位置。

---

## 阶段 5：失败处理与回归

审查结果为 `FAIL` 时，不进入下一阶段。使用：

```text
Prompts/14_BUGFIX_AND_REGRESSION.md
```

固定步骤：

1. 复现问题。
2. 增加能够稳定失败的测试或验证条件。
3. 记录根因。
4. 采用最小修复。
5. 运行关联测试。
6. 运行当前里程碑完整回归。
7. 再次执行里程碑审查门禁。

以下变化不得作为普通 Bug 修复直接实施，必须提交 Change Request：

- 改变 Assembly 依赖方向
- 改变 Content Schema
- 改变存档格式
- 新增第三方包
- 修改固定 Tick 频率
- 绕过内容验证器
- 改变 Stable ID 规则
- 建立只服务于单个角色、技能或地图的一次性框架系统

使用模板：

- [Change Request 模板](Templates/CHANGE_REQUEST_TEMPLATE.md)
- [ADR 模板](Templates/ADR_TEMPLATE.md)

## 阶段 6：里程碑通过后的操作

里程碑通过后，由人工完成：

1. 填写 `Templates/MILESTONE_ACCEPTANCE.md`。
2. 保存 Codex 结果报告。
3. 保存测试日志、性能结果和构建产物位置。
4. 人工检查 Git diff。
5. 合并分支或 PR。
6. 创建对应 Git 标签。
7. 更新 `PROMPT_RUN_LOG.csv`。
8. 再进入下一个里程碑。

建议标签：

```text
framework/m0-accepted
framework/m1-accepted
...
framework/m10-frozen
```

## 阶段 7：M10 框架冻结条件

M10 完成后，至少需要证明：

1. 新角色能够通过配置新增。
2. 新技能能够通过已有模块组合新增。
3. 新构筑能够通过标签、Synergy 和 Evolution 新增。
4. 新地图能够通过 MapDefinition、场景和 Encounter 新增。
5. 第二角色、第二技能和第二地图的无代码扩展测试通过。
6. 模拟层不引用 Sprite、Prefab、Scene、AudioClip 或 Steam。
7. View 不直接修改 Simulation Store。
8. 存档保存稳定 ContentId，不保存 RuntimeIndex。
9. Release 构建不能包含 Placeholder。
10. 正式 AI 资源没有 provenance 时构建失败。
11. 正式第三方资源没有许可证或 Notice 时构建失败。
12. 30 分钟 Soak 没有持续内存增长。
13. 固定种子的关键测试可复现。
14. Windows Release Build 可从干净 clone 生成。
15. 所有用户可见文本使用本地化 Key。
16. Steam 不可用时游戏仍能完整运行。

完整标准见：

- [框架完成定义](Repository_Docs/Docs/DEFINITION_OF_DONE.md)

未满足这些条件时，不开始大规模正式内容生产。

## 阶段 8：正式角色、技能、构筑和地图生产

框架冻结后，新增正式内容时使用：

```text
Prompts/16_CONTENT_ADDITION_PROMPT.md
```

内容新增应优先只增加：

- Authoring 内容资产
- Map Scene
- Encounter 配置
- Visual Profile
- Audio Profile
- 本地化条目
- 解锁条件
- AI 资产 provenance

新增普通内容时，不应修改：

- Simulation 核心 Store
- Damage Pipeline
- Save Schema
- Content Registry 核心
- UI 主流程
- 平台适配接口

若现有模块无法表达设计，应先提交 Change Request，再决定是否新增底层模块；不得把特殊逻辑硬编码进单个角色、技能、构筑或地图。

# 六、关键判断标准

当 Codex 声称“框架可扩展”时，至少应能提供以下证据：

- 新增第二角色时没有修改核心程序集。
- 新增第二技能时只组合已有 Trigger、Targeting、Delivery 和 Effect。
- 新增第二地图时只增加 MapDefinition、Scene 和 Encounter。
- 存档能保存和恢复新内容的稳定 ID。
- 内容验证器能识别重复 ID、缺失引用和非法进化条件。
- 正式构建能阻止 Placeholder、缺失 provenance 和缺失第三方许可。
- 固定种子的战斗、升级候选和刷怪结果可复现。
- 表现资源被替换后，模拟结果不变。

只有这些证据成立，项目才真正具备后续动态新增角色、技能、构筑和地图的能力。
